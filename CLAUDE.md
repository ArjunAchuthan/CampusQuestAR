# Agent Instructions

> This file is mirrored across CLAUDE.md, AGENTS.md, and GEMINI.md so the same instructions load in any AI environment.

You operate within a 3-layer architecture that separates concerns to maximize reliability. LLMs are probabilistic, whereas most UI and app logic benefits from consistency. This system fixes that mismatch — adapted here for a frontend web app rather than a data/automation pipeline.

## The 3-Layer Architecture

**Layer 1: Directive (What to build)**
- SOPs written in Markdown, live in `directives/`
- One file per screen or feature: goal, inputs, tools/components to use, outputs, edge cases
- Natural language instructions, like you'd give a frontend engineer joining the project mid-sprint

**Layer 2: Orchestration (Decision making)**
- This is you. Your job: intelligent routing.
- Read the relevant directive, edit/create the right component files in the right order, run the dev server to verify, handle errors, ask before large structural changes, update directives with what you learn
- You're the glue between intent and implementation. E.g. you don't invent a new visual pattern for a screen — you check `design-reference/` first, then implement it as a component per the directive

**Layer 3: Execution (Doing the work)**
- The actual app: React + TypeScript components in `src/`, Firebase calls, the Vite build
- This replaces the Python `execution/` scripts of the general-purpose template — here, "deterministic execution" means real, working, testable components and typed functions instead of inline logic scattered across files
- Environment variables (Firebase config, any API keys) live in `.env`, never committed

**Why this works:** if you do everything ad hoc, errors and visual drift compound across screens. Pushing structure into directives and components means you focus on decision-making, not reinventing patterns per screen.

## Operating Principles

**1. Check `design-reference/` and existing components first**
Before styling anything new, check whether `design-reference/` (the cleaned Figma Make export) already establishes the pattern — spacing, glass treatment, color tokens, animation curves. Don't invent a new visual language for one screen. Before writing new logic, check whether an existing component, hook, or lib function in `src/` already does it.

**2. Self-anneal when things break**
- Read the error message and stack trace (build error, runtime error, or visual regression against `design-reference/`)
- Fix the component/logic and verify with `npm run dev` (unless the fix touches paid APIs/quotas — e.g. Firebase billing tier — in which case check with the user first)
- Update the relevant directive with what you learned (a library quirk, a mobile-Safari permission gotcha, a Firestore rule that was needed)
- Example: `getUserMedia` silently fails on iOS Safari over HTTP → you discover it needs a secure context → you note this in `directives/camera-scan.md` so it's not rediscovered next session

**3. Update directives as you learn**
Directives are living documents. When you discover a browser quirk, a better component boundary, a Firestore rule you needed, or a common error — update the directive. Don't create or overwrite directives without asking, unless explicitly told to. Directives are the instruction set for this project and should be preserved and improved over time, not used once and discarded.

## Self-annealing loop

1. Fix it
2. Verify it (`npm run dev`, click through the affected screen against `design-reference/`)
3. Update the directive to include what changed and why
4. System is now stronger for the next feature

## File Organization

**Deliverables vs Intermediates:**
- **Deliverables**: the working app in `src/`, shipped via Firebase Hosting/Vercel — this is what the user (and event participants) actually use
- **Intermediates**: build output (`dist/`), local caches — regenerated by `npm run build`, never hand-edited, never committed

**Directory structure:**
- `design-reference/` — the cleaned Figma Make export. Read-only source of truth for visuals: the glass nav bar, screen layouts, color tokens (`--accent`, safe-area variables), animation timing. Reference it, don't edit it.
- `src/` — the actual app (components, screens, lib, store)
- `directives/` — SOPs in Markdown, one per screen/feature (the instruction set)
- `.env` — Firebase config and any API keys, in `.gitignore`
- `.env.example` — same keys with placeholder values, committed, so the project is reproducible

**Key principle:** `design-reference/` is for visual truth only, never for logic — don't port its placeholder/inline styles wholesale without checking whether the directive for that feature calls for real data or behavior now.

## Summary

You sit between human intent (directives) and working app code (components, Firebase). Read instructions, make decisions, check the design reference, implement, verify, continuously improve the system.

Be pragmatic. Be reliable. Self-anneal.
